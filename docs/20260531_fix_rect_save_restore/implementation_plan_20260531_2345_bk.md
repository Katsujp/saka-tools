# 実装計画書：無限ロードの根絶 ＆ 解析実行ボタンフリーズの完全解消

「ローカルから復元」でアライメントを復元した際、画面右上の同期中アイコン（Running）が断続的に動き続けて無限ロード（再実行ループ）になり、「解析を実行」ボタンが反応しなくなる重大な仕様バグを、**「Key-swapping（アップローダーのキー動的リセット）設計」**によって完璧に解決するための計画です。

---

## 🔍 原因分析

### 1. 画面右上の同期中アイコンが断続的に動き続ける原因（ファイルアップローダーの無限 `st.rerun()` ループ）
- **Streamlit の `file_uploader` の永続的評価仕様**:
  Streamlit の `st.file_uploader` は、ユーザーがブラウザ上でアップロードしたファイルを削除するか、コンポーネント自体が破棄されない限り、再実行（`st.rerun()`）された後も **ずっと `uploaded_config is not None`（ファイルが入った状態）を保持し続けます**。
- **前回のコードの問題点**:
  前回の実装では、ローカルからJSONを復元する処理の末尾で `st.rerun()` を呼び出していました。しかし、再実行された後もアップローダーにはJSONファイルがセットされたままになっているため、再び復元処理に入り、`st.rerun()` を呼び出し、また最初に戻って復元処理に入る…という**無限ロード（Running）ループ**が Python 側で発生していました。
- **「解析を実行」ボタンが動かない真の要因**:
  この無限再実行ループにより、Pythonスクリプトが絶え間なく再起動され続けていました。そのため、JSコンポーネントから送信された「解析を実行（`trigger_analysis`）」などのメッセージが Python 側に届いて処理される前にスクリプトが強制破棄・再実行されてしまい、ボタンが完全にフリーズした（押しても解析が動かない）状態になっていました。

---

## 🛠️ 対策案（提案内容）

Python側の無限ループを100%根絶し、復元後にアップローダーを完全に空っぽ（クリア状態）にリセットして、解析実行ボタンが即座に確実に動作するプレミアムな極上設計を適用します。

### 1. 「Key-swapping（キーの動的切り替え）」によるアップローダーのクリーンリセット
- `st.file_uploader` に設定するキーを、固定値ではなくセッション状態から取得する動的キー `st.session_state.uploader_key` に変更します。
  - 初期化: `st.session_state.uploader_key = "restore_uploader_0"`
- JSONファイルの復元処理が完了し、セッション状態への書き戻しが成功したタイミングで、キーの値を現在のタイムスタンプ（例：`restore_uploader_1780234567`）に変更します。
  ```python
  st.session_state.uploader_key = f"restore_uploader_{int(time.time())}"
  ```
- キーが変更された後に `st.rerun()` を実行します。
- スクリプトが再実行された際、アップローダーのキーが変更されているため、Streamlit はこれを**全く新しいコンポーネントとして認識**し、アップロードされていたファイル情報をクリアして完全に「空（`None`）」の状態で再描画します。
- これにより、再実行後は `uploaded_config is None` になり、復元による無限再実行ループが**物理的に100%確実に根絶**されます。画面右上の同期中アイコンもピタッと止まり、通常の待機状態になります。

### 2. 重複排除メッセージング設計との併用
- 計画済みの「JS側の `msg_id` 付与」および「Python側の `last_processed_msg_id` 重複排除ガード」と組み合わせることで、復元後は無限ループが完全に解消され、さらに「解析を実行」ボタンを押した際も明示的なクリックイベント（新しい `msg_id`）として Python 側で瞬時に確実にキャッチされ、解析処理が100%確実に始まります。
