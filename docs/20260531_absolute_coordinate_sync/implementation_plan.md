## 🚨 エラーの原因究明 (バグ診断)

プレビュー画面で青枠が数値を完璧に囲んでいる（日本語文字は完全に枠の外にある）にもかかわらず、OCRで誤読（決定力541➔461、キック力536➔空欄等）が発生する原因について、ゼロベースで処理フローを徹底的に最終検証した結果、**5つの設計的要因（不整合）**を特定いたしました。

### 1. 【要因①：最致命】Streamlit双方向通信の競合による「最新座標の消失（上書き）」
*   **原因**:
    JavaScript側で「選択座標で解析を実行」ボタンを押した瞬間、JSの内部関数（`triggerAnalysis`）は、以下の2つのメッセージを極めて短いミリ秒単位で連続送信しています。
    1. `notifyStateChange()` ➔ Python側に最新スライダー状態を送信 (`update_state`)
    2. `sendMessage("trigger_analysis", {})` ➔ Python側に解析実行シグナルを送信 (`trigger_analysis`)
*   **上書きの発生**:
    Streamlitカスタムコンポーネントの仕様上、短い時間での連続送信は最後のメッセージで上書きされるため、**ユーザーが最後にスライダーで調整した完璧な座標データがPython側に届かず、初期値（`0 px`, `1.0x`）またはズレた状態のままOCR解析が実行されてしまっていた**ため、大誤読を引き起こしていました。

### 2. 【要因②】OCR実行時における「生画像からの自動トリミング再実行」による数pxの境界ブレ
*   **原因**:
    プレビュー画像生成時にはトリミング済みの画像を使用していましたが、**OCR実行時には `app.py` から元の「トリミング前の生画像」をOCRエンジンにそのまま渡してしまっていました**。
    これにより、OCRエンジン内部で再び `scan_game_boundary`（自動境界スキャン）が実行されていました。
*   **結果**:
    境界検出は画像の明暗差を動的にスキャンするため、わずかなノイズや色調によって、検出値が数ピクセル動的に変化（ブレ）します。プレビュー時とOCR実行時でトリミングが数ピクセルでもブレてしまうと、アライメントは完全に狂ってしまい、誤読を招いていました。

### 3. 【要因③】PythonからJSへの状態引数の引き渡し不足による「リラン時の座標リセット」
*   **原因**:
    `fitting_hud` のコンポーネント呼び出し時の引数に、現在調整された `st.session_state` のスライダーパラメータ（`group_scales` や `individual_offsets` など）を一切引き渡していません。
*   **結果**:
    OCR実行や他の操作によって Streamlit が再実行（リラン）された際、Iframe（HTML）側のパラメータが初期値に勝手にリセットされてしまい、Python側とフロントエンド側で座標のミスマッチが恒常的に発生していました。

### 4. 【要因④：超微細バグ】Math.round（四捨五入）と int（切り捨て）の数学的不整合による1pxズレ
*   **原因**:
    *   JS側（`calculateROI`）のサイズ計算：`Math.round(defW * totalScaleX)` （四捨五入）
    *   Python側（`calculate_dynamic_roi`）のサイズ計算：`int(def_w * total_scale_x)` （切り捨て / 少数切り落とし）
*   **結果**:
    この丸め処理の微細な違いにより、サイズ（幅・高さ）において **1px〜2px の不整合（サイズズレ）が恒常的に発生**し、切り出し範囲が微妙に狂って文字の端っこが削れる、あるいはメーターの境界線を巻き込む原因になっていました。

### 5. 【要因⑤：OCRの頑健性】EasyOCRの最初の検出結果への過度な依存
*   **原因**:
    現在、検出されたテキストのうち最初のオブジェクト（`ocr_results[0]`）のみを結果として無条件で採用する仕様になっています。
*   **結果**:
    画像内にわずかでもメーターの端やゴミ文字が写り込み、それが「最初のオブジェクト」として認識されてしまうと、本物の数字が無視されて大誤読を引き起こしていました。

## 🛠️ 提案する具体的な解決策 (承認後に実施)

これらの不整合を完全に封殺し、プレビューの完璧な見た目とOCRのスキャン結果を「1pxの狂いもなく」100%完全に同期させます。

### 対策①：単一メッセージへの「座標データと実行シグナルの統合」（通信上書きの排除）
JS側でボタンを押した際、メッセージを2回に分けるのを廃止し、**`trigger_analysis` の中に現在の最新スライダー状態をすべて同梱して一括送信**します。これで通信の競合を100%完全に排除し、画面で見ている完璧なスライダー位置をダイレクトにOCRへ引き渡します。

#### 【JavaScript側設計 (`triggerAnalysis`)】
```javascript
function triggerAnalysis() {
    sendMessage("trigger_analysis", {
        isGk: state.isGk,
        activeItems: state.activeItems,
        global_scale_x: state.g_s_x,
        global_scale_y: state.g_s_y,
        global_offset: [state.g_x, state.g_y],
        group_scales: state.group_scales,
        group_offsets: state.group_offsets,
        individual_scales: state.individual_scales,
        individual_offsets: state.individual_offsets
    });
}
```

#### 【Python側設計 (`app.py`)】
`trigger_analysis` メッセージ受信時に、同梱された全スライダーデータで `st.session_state` を強制同期させてからOCRを走らせるよう修正します。

---

### 対策②：トリミング画像の一本化キャッシュと再トリミングの完全廃止
*   **`app.py` 側**:
    画像ロード時に「トリミングおよび1920x1080正規化を完了した状態のPIL画像」を `st.session_state.normalized_image` にキャッシュ保存し、プレビューとOCR実行（`extract_all_parameters`）の両方でこのキャッシュ画像を共有します。
*   **`ocr_engine.py` 側**:
    `preprocess_image` 処理において、すでにトリミング・正規化済みの画像が渡された場合は、境界検出をスキップするバイパス用フラグ（`is_preprocessed=True`）を追加し、トリミングの動的なブレを **「物理的に0%（発生不可能）」** にします。

---

### 対策③：Python ➔ JS への全状態スライダー値の引数同期
`fitting_hud` コンポーネントの呼び出し引数として、すべてのスライダーパラメータを明示的に追加します。HTML/JS側では、ロード完了時にこれらのパラメータを読み取って初期状態として復元し、リラン時のパラメータ初期化を完璧に防止します。

---

### 対策④：丸め処理（四捨五入）の厳密な統一
Python側（`ocr_engine.py`）の座標計算においても、`int()` による切り捨てを廃止し、JavaScript側の `Math.round()` と100%整合する四捨五入処理（`round()`）に修正し、計算誤差による1pxのズレも完全に排除します。
```python
final_w = round(def_w * total_scale_x)
final_h = round(def_h * total_scale_y)
```

---

### 対策⑤：OCR文字列抽出アルゴリズムの堅牢化（最重要・ノーミス化）
*   `ocr_engine.py` で、検出されたすべてのテキスト要素全体をループ処理し、**「最初に数値として正しく変換できた3桁または4桁の正当な範囲の数値（100〜9999）」**が見つかった時点で、それを本物のパラメータ数値として採用するロジックに改修します。
*   これにより、万が一余白にゴミが写り込んでも自動的に完全にスルーし、本物の数値だけを狙い撃ちで100%確実に抽出します。
